# Аудит интеграции ЮKassa

## Итоговый статус
Техническая часть оплаты, webhook, сверки, отмены `waiting_for_capture` и возвратов реализована, но боевой запуск пока заблокирован ручными и юридическими проверками.

Критические технические риски в коде исправлены: добавлена локальная таблица платежных попыток, стабильный `Idempotence-Key`, защита от дублей, сверка webhook через API ЮKassa, проверка суммы/валюты/записи, идемпотентная обработка повторных webhook и служебная сверка зависших платежей.

Перед реальной эксплуатацией остаются обязательные проверки: резервная копия production-базы, применение миграций на сервере, production dry-run сверок, webhook URL и события в кабинете ЮKassa, фискальные чеки/receipt, затем контрольный тест в тестовом магазине или по согласованному сценарию.

## Текущая архитектура
Фактический процесс после исправлений:

```text
Клиент выбирает дату, время, формат и способ оплаты
-> сайт создает запись на консультацию
-> если выбрана онлайн-оплата, создается локальная платежная попытка
-> локальная попытка получает стабильный Idempotence-Key
-> сервер создает платеж в ЮKassa
-> ссылка оплаты сохраняется в записи и в yookassa_payments
-> клиент переходит в ЮKassa
-> ЮKassa присылает webhook
-> сервер запрашивает актуальный платеж через API ЮKassa
-> сервер сверяет providerPaymentId, appointmentId, сумму и валюту
-> локальный платеж и запись обновляются
-> уведомления владельцу отправляются после фиксации статуса
```

Платежи привязаны к `appointment_requests`. Отдельной публичной страницы "успех оплаты" пока нет; `return_url` берется из `YOOKASSA_RETURN_URL`, затем `NEXT_PUBLIC_SITE_URL`, затем `siteUrl + /contacts`.

## Найденные критические проблемы
P0 до исправления:

- `Idempotence-Key` создавался заново внутри каждого запроса к ЮKassa и не сохранялся в БД.
- Не было отдельной локальной таблицы платежных попыток.
- Повторный запрос оплаты мог создать новый платеж для той же записи.
- Webhook доверял входящему JSON как источнику `appointmentId`.
- Webhook не сверял сумму и валюту с локально ожидаемыми значениями.
- Повторный webhook мог повторно создавать историю и отправлять уведомления.

P0 после исправления: закрыто в коде.

## Высокий приоритет
P1:

- Фискальные чеки не реализованы в payload создания платежа. Нужно подтвердить требования магазина ЮKassa и добавить `receipt`, если магазин обязан передавать чеки через API.
- `return_url` не является страницей проверки статуса платежа. Это безопасно, потому что он не подтверждает оплату, но UX лучше доработать отдельной страницей статуса.
- На сервере нужно выполнить миграции `0028_yookassa_payment_attempts.sql` и `0029_yookassa_refunds.sql` только после резервной копии и предварительной проверки дублей.

## База данных
Основные поля в `appointment_requests`:

- `paymentMethod`
- `paymentStatus`
- `yookassaPaymentId`
- `paymentAmount`
- `paymentLink`
- `paymentNote`
- `notificationStatus`

Новая таблица `yookassa_payments`:

- `id` — локальный ID платежной попытки.
- `appointmentId` — связь с записью.
- `provider` — сейчас `yookassa`.
- `providerPaymentId` — ID платежа ЮKassa.
- `idempotenceKey` — стабильный ключ запроса.
- `amountKopeks` — сумма в копейках.
- `currency` — ожидается `RUB`.
- `status` — локальный статус.
- `providerStatus` — сырой статус ЮKassa.
- `confirmationUrl` — ссылка оплаты.
- `errorCode` — короткая техническая ошибка без секретов.
- `processedAt`, `notifiedAt`.

Ограничения:

- `UNIQUE(provider, provider_payment_id)`
- `UNIQUE(idempotence_key)`
- индекс по `appointment_id`

## Webhook
Webhook расположен в `app/api/yookassa/webhook/route.ts`.

Что делает:

- принимает входящий webhook без вывода payload в логи;
- берет только `object.id`;
- ищет локальный платеж в `yookassa_payments`;
- запрашивает актуальный платеж через API ЮKassa;
- сверяет `metadata.appointmentId`, сумму и валюту;
- не подтверждает платеж при несовпадении;
- не повторяет бизнес-действия при повторном webhook;
- отправляет уведомление владельцу только один раз после подтверждения оплаты.

Webhook не должен ломать успешную оплату, если Telegram или email временно недоступны: ошибка уведомления сохраняется в `errorCode`/истории, но статус платежа не откатывается.

## Создание платежа
Платежи создаются через `src/lib/appointment-payments.ts`.

Сумма:

- определяется только сервером через `YOOKASSA_PAYMENT_AMOUNT_RUB`;
- переводится в копейки;
- frontend не передает доверенную сумму;
- валюта всегда `RUB`.

Idempotence:

- ключ создается до запроса в ЮKassa;
- сохраняется в `yookassa_payments`;
- повторный запрос с существующей актуальной ссылкой переиспользует ее;
- оплаченная/отмененная запись не получает новый платеж.

## Чеки
В коде сейчас нет `receipt` при создании платежа.

Это нужно подтвердить вручную в кабинете ЮKassa:

- нужна ли фискализация через ЮKassa;
- какие данные нужны для чека;
- ставка НДС;
- предмет расчета и способ расчета;
- email/телефон клиента для чека.

Если чеки обязательны, интеграция пока не полностью готова к реальным платежам.

## Возвраты
Реальные возвраты реализованы через API ЮKassa:

- полный возврат через `POST /v3/refunds`;
- частичный возврат через `POST /v3/refunds`;
- сумма полного возврата рассчитывается сервером;
- частичная сумма проверяется сервером;
- нельзя вернуть больше доступного остатка, ноль или отрицательную сумму;
- полный возврат требует ручное подтверждение `ВОЗВРАТ`;
- параллельные возвраты сериализуются через advisory lock;
- `refund.succeeded` перепроверяется через `GET /v3/refunds/{id}`;
- ручной возврат из кабинета ЮKassa создается локально при webhook;
- `canceled` refund не переводит платеж в `refunded`;
- отмена записи не выполняет автоматический возврат.

Финансовые API возвратов и отмены доступны только при действующей админской сессии.

## Что нужно настроить вручную
В кабинете ЮKassa:

1. Проверить `Shop ID`.
2. Проверить активный `Secret Key`.
3. Указать webhook URL:

```text
https://luneva-psy.ru/api/yookassa/webhook
```

4. Включить события платежей:

```text
payment.succeeded
payment.canceled
payment.waiting_for_capture
```

5. Проверить `return_url`:

```text
https://luneva-psy.ru/contacts
```

или будущую отдельную страницу статуса оплаты.

6. Подтвердить требования по фискальным чекам.
7. Выполнить один тестовый платеж на минимальную сумму или через тестовый магазин.

На сервере:

```text
npm run db:migrate
npm run build
pm2 restart luneva-platform --update-env
```

Служебная сверка зависших платежей:

```text
npm run payments:reconcile
```

## Финальный чек-лист реального платежа
1. Создать тестовую запись на свободное время.
2. Выбрать онлайн-оплату.
3. Убедиться, что сайт выдал ссылку ЮKassa.
4. Проверить в админке, что запись имеет статус оплаты `invoice_sent` или `waiting`.
5. Оплатить минимальную сумму в тестовом режиме или через тестовый магазин.
6. Дождаться webhook.
7. Проверить, что в админке статус стал `paid`.
8. Проверить, что в истории записи есть событие ЮKassa.
9. Проверить Telegram владельцу.
10. Проверить email владельцу.
11. Повторно отправить тестовый webhook и убедиться, что уведомление не задублировалось.
12. Проверить отмененный платеж: статус должен стать `cancelled`, запись не должна считаться оплаченной.

## Итог
Интеграция стала значительно безопаснее и ближе к эксплуатации. Основные блокирующие технические риски закрыты в коде. До статуса "готово" остаются ручная настройка webhook в кабинете ЮKassa, подтверждение фискальных чеков и тест реального сценария оплаты.

## Отмена платежей
Текущий режим платежей одностадийный: `capture: true`. Двухстадийная схема специально не включалась.

Для возможного статуса `waiting_for_capture` добавлена отдельная операция отмены авторизации через API ЮKassa:

```text
POST /v3/payments/{payment_id}/cancel
```

Отмена записи в админке не выполняет возврат автоматически.

## Полные возвраты
Полный возврат выполняется сервером через `POST /v3/refunds`. Перед запросом создается локальная запись `yookassa_refunds` со стабильным `Idempotence-Key`.

Сумма полного возврата рассчитывается только на сервере:

```text
оплачено - успешные возвраты - активные возвраты
```

Для полного возврата администратор должен подтвердить действие словом `ВОЗВРАТ`.

## Частичные возвраты
Частичный возврат доступен только из админки. Сервер проверяет сумму в копейках, валюту `RUB`, статус платежа в ЮKassa и доступный остаток. После частичного возврата статус записи становится `partially_refunded`, а не `refunded`.

## Возвраты из кабинета ЮKassa
Если возврат создан вручную в кабинете ЮKassa, сайт обрабатывает `refund.succeeded`, запрашивает возврат через API и создает локальную запись с `requestedBy = yookassa_dashboard`.

Если локальный платеж не найден, событие фиксируется как `manual_review`.

## Webhook refund.succeeded
Webhook не доверяет входящему JSON. Для возврата используется только ID возврата, затем выполняется запрос:

```text
GET /v3/refunds/{refund_id}
```

После сверки суммы, валюты, платежа и записи сайт обновляет `yookassa_refunds`, `yookassa_payments`, `appointment_requests`, историю и уведомления. Повторный webhook не должен дублировать действия.

## Чеки при возвратах
Структура возвратов содержит `receiptStatus`, но объект `receipt` для платежей и возвратов не добавлен, потому что налоговые параметры проекта не подтверждены.

Перед боевыми возвратами нужно определить `vat_code`, `payment_mode`, `payment_subject`, правила полного и частичного возврата пакетов консультаций.

## Передача оплат и возвратов в админку
Админка получает финансовую сводку по записи: сумма оплаты, возвращено, доступно к возврату, статус платежа, ID платежа ЮKassa, последний возврат и допустимые действия.

## Уведомления клиенту и владельцу
После успешной оплаты владелец получает уведомление через существующий канал Telegram + email.

После успешного возврата владелец получает тип возврата, клиента, запись, сумму возврата, остаток, ID платежа/возврата и причину. Клиент в личном кабинете получает уведомление о возврате, если запись привязана к пользователю.

Ошибки Telegram/email не откатывают финансовую операцию.

## Сверка финансовых операций
Добавлены команды:

```powershell
npm run payments:reconcile -- --dry-run
npm run refunds:reconcile -- --dry-run
```

Без `--dry-run` скрипты могут обновлять локальные статусы на основании API ЮKassa. Сверка не является публичным endpoint.
