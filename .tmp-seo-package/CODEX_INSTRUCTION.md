# Инструкция для Codex: заполнение SEO-полей статей Luneva Psy

## Цель
Заполнить существующие статьи на `https://luneva-psy.ru/blog` данными из `articles-seo.json` через текущую модель данных/админ-панель. Не создавать новые статьи и не изменять основной текст.

## Жёсткие ограничения
1. Сначала изучи репозиторий и найди модель Article/Post, API админки и форму редактирования.
2. Не меняй `slug`, URL, основной текст статьи, категорию, статус публикации и дату.
3. Сопоставляй статью сначала по полному `url`, затем по `slug`. Не сопоставляй по заголовку, если найдено несколько совпадений.
4. Заполняй поля:
   - `h1` ← `h1`
   - `image`/`coverImage` ← `image` только если файл реально существует; иначе оставь текущее изображение и запиши предупреждение
   - `imageAlt` ← `image_alt`
   - `seoTitle`/`metaTitle` ← `seoTitle`
   - `seoDescription`/`metaDescription` ← `seoDescription`
   - FAQ-поле ← `faq` как массив объектов; если поле хранит строку, записать строго валидный JSON из `faqJson`
5. Не вставляй `primaryKeyword` в текст искусственно. Сохрани его только в SEO-поле, если такое поле уже существует.
6. Не добавляй FAQPage JSON-LD вручную в HTML. Используй существующий генератор structured data. Если генератора нет — реализуй один общий безопасный компонент, который строит `FAQPage` из сохранённого FAQ.
7. Не публикуй медицинские обещания, диагнозы или гарантии результата.
8. Для self-harm статей не добавляй вымышленные телефоны помощи. Сохрани информационный дисклеймер и существующую логику экстренной помощи.

## Дубликаты
В файле есть `isLikelyDuplicate` и `canonicalSuggestion`. На этом этапе НЕ удаляй страницы и НЕ делай редиректы автоматически. Только:
- сформируй отдельный отчёт о дубликатах;
- если модель уже содержит поле canonical, можешь заполнить его значением `canonicalSuggestion`;
- если canonical-поля нет, не меняй схему без согласования.

## Порядок работы
1. Сделай резервную копию таблицы/коллекции статей.
2. Создай импорт-скрипт, например `scripts/import-article-seo.ts`.
3. Поддержи режимы:
   - `--dry-run` — ничего не записывает, выводит найденную статью и изменения;
   - `--apply` — применяет изменения;
   - `--slug=<slug>` — обработка одной статьи.
4. Запусти `--dry-run` для всех материалов.
5. Сохрани отчёт `article-seo-import-report.json` с полями: slug, matched, changedFields, warnings, duplicate, error.
6. Убедись, что количество сопоставленных записей равно количеству элементов JSON. Несопоставленные записи не создавать автоматически.
7. После подтверждения выполни `--apply`.
8. Проверь минимум 5 страниц вручную: обычную статью, РПП, подростковую тему, self-harm и страницу-дубликат.
9. Запусти lint, typecheck, тесты и production build.

## Проверки результата
- На каждой странице ровно один H1.
- `<title>` и meta description уникальны.
- FAQ JSON валиден и не отображается как сырой JSON.
- FAQPage выводится только когда FAQ непустой.
- Изображение имеет содержательный `alt`.
- Никакая статья не пропала из `/blog`.
- Старые URL открываются без 404.
- Основной текст не изменён.

## Финальный отчёт
Покажи таблицу: URL | найдено | SEO Title | Description | FAQ | изображение | предупреждения.
Отдельно перечисли вероятные дубли и предложи план canonical/301, но не применяй его без подтверждения Андрея.
